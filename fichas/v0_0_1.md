# Biblioteca v0.0.1 — Ficha técnica de preparación de base

## 1. Propósito de la versión

La versión **v0.0.1** de **Biblioteca** no tiene como objetivo implementar nuevas funcionalidades de lectura, interfaz, anotaciones o diccionario.

Su propósito es dejar preparada una **base técnica estable, local e independiente** a partir del código de **Readest**, para que el equipo pueda comenzar el desarrollo propio de Biblioteca sobre una sustancia ya funcional.

Esta versión debe responder a una pregunta concreta:

> ¿Tenemos una copia local de Readest preparada, ejecutable, aislada del repositorio original y lista para empezar a ser modificada como Biblioteca?

Si la respuesta es sí, la v0.0.1 está cumplida.

---

## 2. Contexto inicial

Se parte de la siguiente situación:

- El proyecto ya ha sido clonado localmente mediante `git clone`.
- El código base procede del repositorio oficial de Readest.
- Todavía no se ha preparado completamente el entorno de desarrollo.
- Todavía no se ha aislado el repositorio local del remoto original.
- Todavía no se ha creado una primera base Git propia de Biblioteca.
- Todavía no se ha confirmado que la app pueda instalar dependencias y arrancar correctamente en local.

El objetivo de esta fase es transformar esa copia inicial de Readest en una base local segura para el desarrollo de Biblioteca.

---

## 3. Definición funcional de la versión

Biblioteca v0.0.1 es una versión **pre-funcional**.

No se espera que el usuario final pueda usar Biblioteca como producto propio todavía.

La versión debe permitir al equipo desarrollador:

1. Tener el código fuente de Readest disponible localmente.
2. Resolver correctamente dependencias, submódulos y workspace.
3. Ejecutar la app en modo desarrollo.
4. Confirmar que la base técnica funciona antes de modificarla.
5. Cortar la relación práctica con el repositorio original de Readest.
6. Crear una rama local propia de Biblioteca.
7. Crear un primer commit local que actúe como punto de restauración.
8. Documentar el estado inicial del proyecto.

---

## 4. Alcance de v0.0.1

### Incluido

Esta versión incluye:

- Preparación del entorno de desarrollo.
- Instalación de dependencias del sistema necesarias para ejecutar el proyecto.
- Instalación de dependencias JavaScript/TypeScript mediante `pnpm`.
- Inicialización de submódulos Git si el proyecto los requiere.
- Verificación del monorepo.
- Verificación de scripts disponibles.
- Ejecución de la app en modo desarrollo web.
- Ejecución de la app en modo escritorio/Tauri, si las dependencias del sistema lo permiten.
- Eliminación del remoto `origin` que apunta al repositorio original de Readest.
- Creación de una rama local `biblioteca`.
- Creación de un primer commit local de base.
- Documentación mínima del estado técnico.

### No incluido

Esta versión no incluye:

- Cambio de branding visual de Readest a Biblioteca.
- Modificación de la interfaz.
- Modificación del lector.
- Modificación del sistema de anotaciones.
- Añadido de tags personalizados.
- Integración con Diccionario.
- Creación de una base de datos propia de Cogito/Biblioteca.
- Integración con SiYuan, Logseq, Obsidian o Zotero.
- Sincronización externa.
- Publicación en GitHub, GitLab u otro remoto.
- Distribución de binarios.
- Empaquetado final para Arch Linux.
- Diseño final de arquitectura modular.

## 5. Estado esperado del repositorio

Al finalizar v0.0.1, el repositorio debe estar en una situación equivalente a:

```text
Biblioteca/
  ├── código base procedente de Readest
  ├── dependencias instaladas
  ├── submódulos inicializados si existen
  ├── rama local biblioteca
  ├── sin remoto origin hacia readest/readest
  └── primer commit local de base
```

El repositorio debe poder gestionarse completamente en local.

No debe depender de GitHub para continuar el desarrollo.

---

## 6. Principio técnico fundamental

Readest se usará como **sustancia inicial** de Biblioteca.

Esto significa:

- Readest no será tratado como dependencia externa viva.
- Readest no será actualizado automáticamente.
- Biblioteca no debe seguir el ritmo de actualizaciones del proyecto original.
- Las actualizaciones futuras de Readest solo se estudiarán manualmente si aportan valor claro.
- La prioridad será estabilizar una base local propia y empezar a construir sobre ella.

Readest funciona aquí como punto de partida, no como autoridad futura del proyecto.

## 7. Flujo técnico de preparación

### 7.1. Verificar ubicación

Desde la raíz del proyecto:

```bash
pwd
ls
```

Se espera estar dentro de la carpeta raíz de Biblioteca, que contiene al menos:

```text
package.json
pnpm-lock.yaml
apps/
packages/
```

La presencia de `package.json` en raíz indica que el proyecto usa un monorepo.

---

### 7.2. Revisar scripts disponibles

```bash
cat package.json
```

Se deben identificar scripts principales como:

```json
{
  "dev-web": "pnpm --filter @readest/readest-app dev-web",
  "tauri": "pnpm --filter @readest/readest-app tauri"
}
```

Esto indica que la aplicación principal vive como workspace interno, no directamente en la raíz.

---

### 7.3. Comprobar `pnpm`

```bash
pnpm -v
```

Si no está instalado:

```bash
sudo pacman -S pnpm
```

El proyecto declara `pnpm` como gestor de paquetes. No debe sustituirse por `npm` o `yarn` salvo decisión técnica explícita.

---

### 7.4. Inicializar submódulos Git

Readest puede depender de piezas internas no descargadas con un clone superficial o incompleto.

Si durante `pnpm install` aparece un error similar a:

```text
ERR_PNPM_WORKSPACE_PKG_NOT_FOUND
"foliate-js@workspace:*" is in the dependencies but no package named "foliate-js" is present in the workspace
```

debe ejecutarse:

```bash
git submodule update --init --recursive
```

Después:

```bash
pnpm install
```

---

### 7.5. Instalar dependencias del proyecto

```bash
pnpm install
```

Esto debe instalar las dependencias JavaScript/TypeScript del monorepo.

Notas:

- Las dependencias del proyecto vivirán principalmente en `node_modules`.
- `pnpm` también usará su store/caché local.
- No se deben commitear `node_modules`.
- Cualquier cambio en `pnpm-lock.yaml` debe revisarse antes de crear el commit base.

---

### 7.6. Ejecutar versión web

```bash
pnpm dev-web
```

Criterio de aceptación:

- El servidor de desarrollo arranca.
- Se muestra una URL local.
- La aplicación puede abrirse en navegador.
- No hay errores críticos de compilación.

---

### 7.7. Ejecutar versión escritorio/Tauri

```bash
pnpm tauri dev
```

Si faltan dependencias del sistema en Arch Linux, instalar según error concreto.

Dependencias probables:

```bash
sudo pacman -S base-devel rust cargo pkgconf webkit2gtk-4.1
```

Criterio de aceptación:

- La app intenta arrancar como aplicación de escritorio.
- Si falla, el error queda documentado.
- La versión web debe tener prioridad para considerar lista la base inicial.

---

## 8. Aislamiento del repositorio original

Una vez confirmado que la base instala y arranca, se debe cortar la relación práctica con el remoto original.

### 8.1. Ver remotos

```bash
git remote -v
```

Si aparece:

```text
origin  https://github.com/readest/readest.git
```

significa que el repositorio local sigue apuntando al proyecto original.

### 8.2. Eliminar remoto original

```bash
git remote remove origin
```

### 8.3. Confirmar eliminación

```bash
git remote -v
```

La salida debería estar vacía.

Esto deja el proyecto completamente local.

---

## 9. Rama local de desarrollo

Crear una rama propia:

```bash
git checkout -b biblioteca
```

La rama `biblioteca` será la rama inicial del desarrollo propio.

No se trabajará directamente sobre la rama heredada de Readest.

---

## 10. Commit base

Crear un primer commit local que funcione como punto de restauración:

```bash
git add .
git commit -m "Base inicial de Biblioteca desde Readest"
```

Antes de ejecutar el commit, revisar:

```bash
git status
```

No deben incluirse:

```text
node_modules/
dist/
.next/
target/
build/
```

Si alguno aparece, revisar `.gitignore` antes de commitear.

---

## 11. Criterios de aceptación de v0.0.1

La versión v0.0.1 se considera completada cuando:

- El repositorio existe localmente.
- El proyecto conserva el código base de Readest.
- Los submódulos necesarios han sido inicializados.
- `pnpm install` termina correctamente.
- `pnpm dev-web` arranca correctamente.
- `pnpm tauri dev` se ha probado o se ha documentado por qué no arranca todavía.
- El remoto original de Readest ha sido eliminado.
- Existe una rama local llamada `biblioteca`.
- Existe un commit local inicial.
- El equipo puede empezar a inspeccionar y modificar el código sin depender del repositorio original.

## 13. Riesgos identificados

### Riesgo 1: submódulos no inicializados

Síntoma:

```text
ERR_PNPM_WORKSPACE_PKG_NOT_FOUND
```

Solución:

```bash
git submodule update --init --recursive
```

---

### Riesgo 2: dependencias Tauri faltantes en Arch Linux

Síntoma:

Errores relacionados con:

```text
webkit
gtk
pkg-config
cargo
rust
libsoup
```

Solución:

Instalar dependencias del sistema según error concreto.

Comando base probable:

```bash
sudo pacman -S base-devel rust cargo pkgconf webkit2gtk-4.1
```

---

### Riesgo 3: commit accidental de archivos pesados

Síntoma:

`git status` muestra carpetas como:

```text
node_modules/
.next/
target/
dist/
```

Solución:

Revisar `.gitignore` antes del primer commit.

---

### Riesgo 4: dependencia conceptual del upstream

Síntoma:

El equipo sigue pensando en Readest como proyecto vivo que debe actualizarse constantemente.

Solución:

Definir explícitamente que Readest es una base congelada, no una dependencia de actualización continua.
